# + scala-cli run) - a genuine crash-level DISHONEST bug, confirmed purely

#
#   Exception in thread "main" java.lang.NullPointerException: Cannot invoke
#   "java.io.PrintWriter.println(String)" because the return value of

#   	at com.example.cobol.Cc04idxr$.run(Main.scala:1068)
#   	at com.example.cobol.run.main(Main.scala:1065)

# Root cause (traced in generator/file-io-gen.js and generator/
# expression-gen.js, parser/index.js): parser/index.js's
# parseEnvironmentDivision only ever recognizes a `RELATIVE KEY IS <field>`
# clause (round-26 root cause 3's own new `fileControl.relativeKey`) - it has
# no branch at all for `RECORD KEY IS <field>` (the clause INDEXED files use
# instead of RELATIVE KEY), so RELATIVE_KEY_REGISTRY never gets an entry for
# any INDEXED file no matter what its RECORD KEY clause says.
# generator/file-io-gen.js's generateOpen decides whether to build the
# keyed, indexable `bufVar` buffer (vs. the old plain PrintWriter) purely
# from `accessModeFor(fileName)` (RANDOM/DYNAMIC) - so OPEN OUTPUT of this
# RANDOM-access INDEXED file DOES build an (empty) bufVar and does NOT
# create idxFileWriter. But generator/expression-gen.js's
# generateWriteStatement instead gates on `isKeyedAccess(fileName,
# statement)`, which ALSO requires `relativeKeyVarFor(fileName)` to be
# non-null - false here (RECORD KEY was never captured) - so WRITE takes the
# OLD, non-keyed codegen branch that assumes a `idxFileWriter` PrintWriter
# was created by OPEN. It wasn't (OPEN took the keyed/bufVar branch), so
# `idxFileWriter` is still null when the first WRITE statement runs -
# guaranteed NullPointerException for ANY INDEXED file opened
# RANDOM/DYNAMIC and then WRITTEN to, which is the overwhelmingly common
# real-world access pattern for an indexed file (RANDOM/DYNAMIC access is
# the whole point of choosing ORGANIZATION IS INDEXED over a plain
# sequential file). No `???`/TODO marker anywhere warns of this - it
# compiles cleanly and only fails at runtime, on the very first WRITE.
