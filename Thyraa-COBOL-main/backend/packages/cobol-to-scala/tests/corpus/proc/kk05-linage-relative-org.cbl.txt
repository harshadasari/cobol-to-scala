      * kk05 (round 35): round-34's own open question ("does LINAGE even
      * apply to a RELATIVE/INDEXED file in real cobc?") - answered
      * definitively here via a direct GnuCOBOL probe: NO. Combining
      * `ORGANIZATION IS RELATIVE` with a `LINAGE IS <n> LINES` clause on
      * the SAME FD is a hard COMPILE-TIME error under GnuCOBOL 4.0-early-
      * dev.0 - "LINAGE clause with wrong file type" - not merely a
      * runtime concern. An identical probe swapping in `ORGANIZATION IS
      * INDEXED` (with a RECORD KEY clause) produces the SAME compile
      * error. Since real COBOL programs cannot even legally COMBINE these
      * two clauses, this is not "the engine failing to support a
      * documented feature" (there is no valid COBOL program of this shape
      * to support) - it answers the round-34 refuter's own open question
      * rather than reporting a transpiler bug.
      *
      * For completeness: the engine's own convertToScala() does NOT
      * reject this combination at all (it has no FD-clause/organization
      * compatibility validation of any kind) - it silently generates
      * Scala that compiles and runs, treating the RELATIVE file's LINAGE
      * clause exactly like an ordinary LINE-SEQUENTIAL LINAGE file (the
      * WRITE/AT END-OF-PAGE output it produces has no cobc oracle to
      * compare against, since cobc itself never gets past compilation for
      * this input). This is flagged HONEST/out-of-scope, not a new
      * dishonest finding - the engine is more PERMISSIVE than real cobc's
      * own front end here, not silently wrong about a real program's real
      * behavior, and it does not crash or hang on this out-of-scope input
      * either.
